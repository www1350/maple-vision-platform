## v0.2 连续交付顺序

1. 保留 P0/v0.1 的 API、legacy 数据和历史证据；新增格式显式标版本。确认知识计划、生命周期样本、模型运行证据的合同。
2. 验证知识计划的完整源字节/基线、差异、原子回滚与严格幂等；知识应用不热替换运行规则。
3. 冻结 18×48 lifecycle 数据和 manifest SHA-256，验证阶段、位置、标签、会话隔离与实际轨迹。模型训练使用私有输入副本，不改冻结数据。
4. 在同一新 val 上比较旧模型和候选；按已声明准则选模后再做保留 test。分阶段/地图/位置报告误差，模型和像素基线分开。
5. 完成指定模型 suite/soak、资源采样和实际 reinfer 的独立回归。重点验证预检预算、文件变化、模型身份和保留原始失败轮次一次；这些最终行为在验收前保持待验证状态。
6. 运行全树测试、实际 CPU 训练/导出/推理、干净 wheel 安装和准确提交的 Ubuntu/Windows CI。针对真实缺陷补反例，不降低断言或排除失败样本。
7. 分别决定工程平台发布和模型推广。模型未达到门禁时保留失败与旧模型，不授予新模型默认资格；完整 v8、真实域与 24 小时长稳继续单列。

## 证据规则

- 一个发布提交对应准确的测试命令、环境、运行结果与 CI URL；旧提交的绿灯不自动覆盖新修改。
- fixture 实现、fixture 测试通过、模型通过、真实域通过、长稳通过是不同状态。
- `lab replay` 继续只核对动作与环境。新版 `lab reinfer` 实际重新计算感知、监督、策略和终止帧；需要新版证据和同一模型身份，旧包不能补造缺失字段。
- suite/soak 的预期最终行为是保留实际失败轮次一次，不能另跑一遍替代原失败；最终预检/文件变化边界与该保留行为需在当前发布门禁中确认。
- 资源值记录来源、单位、未知原因和采样范围；CPU/RSS 是进程数据，生命周期峰值与本轮最大采样值分别解释。
- 基线和 ONNX 训练/测试数据哈希、阈值与模型哈希必须分别记录；参数或数据变化后重新验证。
- 计划中列出的目标比例不是已有测量值，也不能替代样本数、误差类型和未覆盖范围。
